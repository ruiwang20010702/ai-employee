# 公开增长记分卡

Foursday 的 90 天目标是“有证据的增长”，不是默认埋点。项目不会主动回传数据、
上传本地证据、扫描私有仓库，也不会为了增长数字开启生产能力。

需要获取当前只读公开快照时，运行：

```bash
npm run growth:report -- --sha <经过审核的40位候选提交>
```

命令默认匿名读取 GitHub 公共 API，只输出聚合数字，并检查 Issue #49/#50 是否仍指向同一不可变候选，以及候选是否已从默认分支可见。它不输出用户名或评论正文，不修改 GitHub、不自动发布，也不写生产数据。外部贡献者只按合入当前默认分支的 PR 非维护者作者去重，不统计认领、开放 PR 或宽泛 Contributors API。已合并外部 PR 带 `community-extension`、`recipe` 或 `adapter` 标签时，只记为维护者确认的社区扩展；只有显式提供版本化扩展证据清单，并同时通过本地文件验证和 GitHub 目标回读时，`locallyVerifiedCommunityRecipesOrAdapters` 才会得到数字，否则保持 `null`，不能猜测成 0。若匿名公共限额耗尽，可以通过标准 `GH_TOKEN` 或 `GITHUB_TOKEN` 环境变量认证同一组固定公开仓库请求；令牌不会被输出、保存或转发到其他地址。

当前下一道维护者门禁是：

```bash
npm run pilot:self:verify -- --manifest /absolute/path/maintainer.json --sha <经过审核的提交>
```

只有命令同时证明当前候选的 10 次本地闭环和 10 个在线目标回读，才进入外部 10 人邀请阶段。

公开勾选框只记为“维护者确认数”，不能直接冒充已验证闭环。同一份私有证据格式承担两个不同门禁。90 天进度从第一位真实用户开始累计时，使用：

```bash
npm run growth:report -- --sha <经过审核的提交> --closed-loop-manifest /absolute/path/growth.json
```

此时 `locallyVerifiedClosedLoopUsers` 按不同外部别名加最多 1 位稳定维护者身份计算；维护者重复完成多次闭环不会增加用户数。这一数字本身不能通过公开候选门禁。

完成私有 10 + 10 清单后，再在不输出别名或证据正文的前提下绑定严格首发证据：

```bash
npm run growth:report -- --sha <经过审核的提交> --pilot-manifest /absolute/path/pilot.json
```

严格首发清单必须在顶层声明同一个 `candidateSha`，每一份严格首发证据的起始提交也必须等于该候选。旧候选的有效闭环可以保留在累计闭环清单中，但不能解锁新候选的发布门禁。

该命令会在同一次只读运行中完成两项验证：本地证据完整性，以及清单中每个 Issue 和 Draft PR 的 GitHub 在线回读。在线部分会重新构造批准的合成 Issue，核对仍为打开状态的 Draft PR 字段，并将标题、正文与证据包封存的 SHA-256 比较；最终只输出 `onlineVerifiedPilotTargets` 聚合数量。只有本地 10 + 10、没有在线回读，不能把 `broadLaunchReady` 设为 `true`。

没有成功通过 `pilot:verify` 时，`locallyVerifiedExternalPilotLoops` 必须保持 `null`，`broadLaunchReady` 必须保持 `false`。

社区配方或适配器使用只包含候选提交与公开仓库事实的清单：

```json
{
  "schema": "foursday-community-extension-evidence/v1",
  "candidateSha": "<40位提交>",
  "entries": [{
    "kind": "recipe",
    "extensionId": "community-weekly-review",
    "extensionPath": "examples/recipes/community-weekly-review.json",
    "pullNumber": 123
  }]
}
```

先验证本地扩展，再把证据绑定进聚合报告：

```bash
npm run extensions:evidence:verify -- --manifest /absolute/path/extensions.json --sha <经过审核的提交>
npm run growth:report -- --sha <经过审核的提交> --extension-manifest /absolute/path/extensions.json
```

验证器会拒绝候选漂移、重复 ID、路径或 PR、符号链接、带凭据或契约不合格的扩展，以及固定示例目录外的文件。公开报告还会独立核对引用的 PR 必须由外部作者提交、已经合入当前默认分支、带有经过审核的扩展标签，并且 PR 文件 blob、候选文件 blob 与本地 SHA-256 完全一致，避免把维护者之后重写的文件冒充社区原始贡献。两条命令都不输出贡献者身份，也不修改 GitHub。

## 计数契约

### 成功安装

只有体验者自愿报告固定 SHA 的一条命令成功启动，或者维护者在全新工作区直接复现并
留下有界证据时，才计为一次成功安装。包下载量、CI 任务、重复重试和 `reuse:verify`
创建的两个测试工作区都不计数。

维护者复验命令为 `npm run public-install:verify -- --sha <经过审核的功能提交>`；其 JSON 结果必须明确显示转发凭据令牌 0、外部副作用 0、生产写入 0。这只能作为维护者自己的安装证据，不能冒充外部用户。

外部用户可以使用 Issue #50 中的有界模板；安装签到不会升级成验证闭环用户，也不会产生
仓库或生产权限。

固定提交的 Web 接入页只在只读 readiness 返回 `externalSystemsModified: false` 后生成同一份有界模板。复制发生在本机，打开 Issue #50 和发布评论仍是两次独立的自愿操作；一旦开始准备 fork，“尚未创建 fork”的安装签到复制入口会被禁用。

公开证明不得包含用户名、邮箱、本机路径、令牌、模型输出、私有仓库身份或公司资料。
预览成功不代表已经创建 fork、分支或 PR，更不代表已经合并、部署、发送或执行计划。

### 完成验证闭环的用户

每个明确同意参与的独立用户最多计一次，不按闭环次数重复累计。至少要有一份绑定唯一
Issue 与 Draft PR 的有效证据：完整计划精确审批、目标回读、项目记忆单独确认、时间返还
单独确认均成立。维护者仍需独立回读公开 Issue 和 Draft PR；完整本地证据包不公开上传。

10 分钟接入漏斗使用两段诚实证据：体验者填写的“安装→预览”观察值，以及纳入证据完整性摘要的“本地服务启动→结果确认”单调时钟自动耗时。后者会细分计划生成、人工审查、审批后执行和结果确认，但明确不包含首次包下载；任何一段都不能单独证明完整 10 分钟承诺。

### 外部贡献者

非维护者贡献合入默认分支后才计为已完成外部贡献者。认领留言、Draft PR、Review 和
未完成尝试都是有价值的漏斗信号，但不能提前记为完成。

### 社区配方或适配器

非维护者贡献的无凭据、可版本化配方或适配器，通过契约测试、安全审查并合入后才计数。
改名、重复内容、维护者测试夹具和依赖隐藏生产权限的连接器不计数。

### GitHub Star

只使用 GitHub 仓库公开计数；不购买、不交换、不自动化刷 Star。

## 证据与隐私边界

- 可以公开：Issue/PR 链接、固定提交、受限的计划与证据哈希、Draft/打开状态、自愿反馈和汇总数量。
- 只留本地：完整验证证据包、本机路径、运行日志、项目记忆正文、模型输出和私有仓库信息。
- 禁止公开：凭据、令牌、真实工作消息、员工标识、内部源码或生产数据。
- 增长和产品权限相互独立：任何目标都不能开启生产发送、自动执行、主动工作、合并或部署。

这份记分卡按保守口径计算：缺少证据就是“不计数”，不是“应该已经完成”。
