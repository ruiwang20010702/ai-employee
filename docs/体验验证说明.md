# 体验验证说明

v0.5 不能因为代码测试通过就宣称适合公开增长。正式候选必须先完成 10 次维护者真实闭环，再由 10 名不同的外部体验者依据 Quick Start 独立完成同一闭环。

一次有效闭环必须同时满足：真实合成 Issue、完整计划哈希审批、五步执行全部完成、GitHub Draft PR 逐字段回读、项目记忆与时间返还分别确认，以及确认后导出的 `verified_closed_loop` 证据包。安装、只看预览、测试夹具、重复使用同一 Issue/PR、未确认结果或手写 JSON 都不计数。

外部体验者不需要上游写权限。标准路径是运行 README 中固定完整提交的一条命令，再在回环 Web 页面单独确认 **Prepare my pilot fork**。这次确认只允许创建或复用体验者的个人 fork、在 `~/FoursdayPilot/` 固定私有目录克隆精确提交、绑定无凭据官方 `upstream`，并以禁用生命周期脚本的方式安装锁定依赖；不会调用模型、推送、创建 PR、合并或部署。随后使用公开体验 Issue #49。审批前必须核对页面显示的推送来源 fork、Issue/PR 上游目标和起始提交；完成后证据必须绑定来源 fork、`foursday/` 分支、精确提交、上游 PR、打开状态和 Draft 标记。README 中保留的手工 fork 命令只是备用入口，也必须固定到同一提交。

确认记忆与时间返还后，页面会生成隐私安全体验证明。体验者只把这份白名单摘要粘贴到公开 Issue：它包含公开 GitHub 目标身份、受治理哈希、运行时、已确认返还时间和反馈占位符，不包含记忆正文、内部编号、本机路径、令牌或模型输出。该证明明确属于未签名本人陈述，维护者仍须独立回读 Issue 与 Draft PR。完整证据包禁止公开上传，先保留在本机；只有维护者明确约定私密传输方式后才提供。

页面会在复制按钮旁提供 **Open pilot Issue #49** 链接；打开页面不会自动发布剪贴板内容，体验者必须自行复核并提交。此前在 Issue #50 的安装签到只证明一条命令和只读 readiness 成功，不计入外部完整闭环。

证据文件与 `pilot.json` 保存在不提交的本机私有目录，只使用外部体验者化名，不采集姓名、邮箱、令牌、仓库凭据或模型原始输出。清单格式和完整命令以英文[体验验证契约](./en/pilot-validation.md)为准：

```bash
npm run pilot:verify -- --manifest /absolute/path/to/pilot.json
```

本地证据包完整性与 GitHub 在线回读是两项独立检查：

- **本地 SHA-256 完整性：**证据包内的摘要只能发现封存后的字节是否变化。它不是数字签名，不能证明执行者身份，也不会访问 GitHub 或证明记录的目标仍以原状态存在。
- **GitHub 在线回读：**发布前，维护者必须在 GitHub 上重新打开每个已记录目标并逐字段核对：
  - **Issue：**仓库、编号、URL、状态、标题和正文必须与已批准的变更请求一致。
  - **Draft PR：**仓库、编号、URL、打开状态、草稿标记、源分支、源提交 SHA、目标分支、标题和正文必须与已批准计划及已验证推送一致。

因此，即使本地验证通过，在单独完成上述在线回读前，报告仍会保留 `targetReadbackReverificationRequired: true`。
