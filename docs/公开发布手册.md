# 公开发布手册

Foursday 应靠“陌生用户能安全交出真实工作”的证据获得关注，而不是夸大 Star、安装量或自动化能力。本手册把当前外部体验与后续大范围发布分开，每一句公开表述都要能回到证据。

| Forks | 0 | 还没有外部 fork 被计为完整体验闭环 |

[Issue #49](https://github.com/ruiwang20010702/foursday/issues/49) 和 [Issue #50](https://github.com/ruiwang20010702/foursday/issues/50) 已固定到仓库顶部，分别承接完整体验与低门槛安装签到。固定入口只改善发现，不算安装或闭环。

历史维护者批次仍能证明早期治理契约确实跑通过，但候选变化后不能复用为当前发布证据；当前候选必须重新完成自己的 10/10。

每次更新公开进度前，先运行匿名聚合回读：

```bash
npm run growth:report -- --sha <经过审核的40位候选提交>
```

报告只读取 GitHub 公开状态，不输出身份或评论正文；只要两个 Issue 指向不同候选、候选尚未进入默认分支，或外部闭环少于 10/10，就不会把大范围发布标记为就绪。

公开勾选数量只是维护者确认。大范围发布门禁还必须通过 `--pilot-manifest` 验证私有 10 + 10 证据清单；同一次运行还会在线逐条回读全部 Issue 与 Draft PR，只有 `onlineVerifiedPilotTargets` 等于完整清单数量时，`broadLaunchReady` 才可能为真。本地证据不能单独解锁发布，报告只输出聚合结果，不输出参与者别名或证据包正文。

邀请外部体验者前，先单独验证当前候选的维护者阶段：

```bash
npm run pilot:self:verify -- --manifest /absolute/path/maintainer.json --sha <经过审核的提交>
```

命令必须同时报告 10 次候选绑定维护者闭环和 10 个在线目标回读；祖先提交上的历史闭环不计入当前门禁。

独立的 `--closed-loop-manifest` 可以从第一位有证据用户开始，持续报告 `locallyVerifiedClosedLoopUsers`，直到 90 天目标的 50 人；它只用于渐进增长统计，不能削弱或替代 10 + 10 首发门禁。

若 GitHub 匿名 API 限额耗尽，可以使用标准 `GH_TOKEN` 或 `GITHUB_TOKEN` 只认证同一组固定公开仓库读取；报告仅记录使用了认证，不输出令牌。

外部贡献进度只按合入默认分支的非维护者 PR 作者统计。配方或适配器标签只是维护者确认，不能单独证明扩展已经通过契约和安全复核。只有同一候选先通过 `npm run extensions:evidence:verify`，再通过 `--extension-manifest` 让增长报告回读合并 PR、审核标签和精确改动文件后，`locallyVerifiedCommunityRecipesOrAdapters` 才能得到数字；缺少任一侧证据时保持 `null`。

## 发布阶段

| 阶段 | 人群 | 必须具备的证据 | 允许的行动号召 |
|---|---|---|---|
| 定向体验 | 维护者能亲自支持的 10 个人 | 不可变一键启动、只读 readiness、明确审批、Draft PR 回读 | 完成一个合成任务，并告诉我第一个卡点 |
| 公开候选 | GitHub 访客和贡献者 | 10/10 独立外部闭环、可复现安装包、公开安全模型、最新真实演示 | 复现闭环、创建 Draft PR 或领取 good first issue |
| 大范围发布 | 开发者社区 | v0.5 已进入默认分支或不可变 Release、外部证据有效、维护者有支持能力 | 运行、批评并贡献，禁止组织投票 |

不能从“维护者自己验证过”直接跳到大范围发布。当前真实里程碑是 10 位不同外部体验者完成闭环，而不是继续增加宣传页面。

## 邀请最初 10 个人

定向邀请最容易发现合格用户为什么完成或放弃。每条邀请都要根据真实关系单独修改，不能群发公司通讯录。

### 中文邀请

> 我在测试 Foursday：一个开源工作分身。它会把一条合成 GitHub Issue 变成经过完整计划审批的代码修改、测试和可回读 Draft PR。预览只需要 Node.js；完整闭环使用你自己的 GitHub 账号，以及 Codex、Claude Code 或兼容模型。它不需要钉钉或生产凭据，也不能合并和部署。你愿意体验一次 10 分钟候选版，并告诉我第一个卡住的地方吗？
>
> 演示：https://github.com/ruiwang20010702/foursday/blob/581bac466d4d9288079b52a180be2310974caf88/assets/foursday-v0.5-demo.mp4
>
> 体验入口：https://github.com/ruiwang20010702/foursday/issues/49

邀请要的是阻力反馈，不是好评、Star 或“必须成功”的结果。

## 公开表述账本

| 当前可以说 | 现在不能说 |
|---|---|
| “v0.5 候选版” | “生产可用的 v0.5” |
| “历史维护者 10/10；当前候选 0/10；外部 0/10” | “当前候选已被 10 位用户验证” |
| “一位维护者复现了公开安装” | “数百次安装”或把下载量当用户数 |
| “已测量服务启动到确认，包下载另计” | “每个人都能在 10 分钟内完成” |
| “Codex、Claude Code 或兼容模型可运行 GitHub 配方” | “支持所有模型和办公平台” |
| “只创建 Draft PR，不合并、不部署” | “完全自主的软件工程师” |

每篇发布内容都应链接真实仓库、75 秒演示，以及安装签到或体验 Issue。不得上传完整私有证据包、模型输出、本机路径、凭据或公司工作内容。

## 渠道规则

### GitHub

- 外部体验开放期间，继续固定 Issue #49 和 Issue #50。
- 仓库简介、Topics、演示和体验进度必须保持真实。
- 在仓库 Settings 上传 `assets/foursday-social-preview.png` 是独立的维护者操作。GitHub 官方建议使用 1280 × 640 图片获得最佳展示；仓库里的候选素材已符合尺寸且小于 1 MB。参见 [GitHub 官方社交预览说明](https://docs.github.com/zh/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/customizing-your-repositorys-social-media-preview)。

### Show HN

只有在外部体验门禁完成，并且可运行的 v0.5 已从默认分支或不可变 Release 直接可见时再发布。维护者必须亲自撰写，不能粘贴 AI 生成或 AI 修改的发布文案。标题应真实、无夸张并以 `Show HN:` 开头；直接链接可运行项目，发布后本人参与讨论，绝不索要投票或组织评论。具体约束以 [Show HN 指南](https://news.ycombinator.com/showhn.html) 和 [Hacker News 社区规则](https://news.ycombinator.com/newsguidelines.html) 为准。

### 其他开发者社区

每个社区都要重新写符合当地语境的内容，不能把同一宣传稿四处复制。先讲清个人问题——做出另一个有边界的“自己”，争取每周拿回一个工作日——再展示真实 Issue 到 Draft PR 闭环、当前外部人数和安全取舍。邀请技术批评和复现，不索要 Star。

## 七天体验推进

1. 每天定向邀请 2 位合格体验者，直到 10 人开始或明确拒绝。
2. 只记录经同意的有界漏斗状态：已打开、readiness 阻断、预览完成、fork 已准备、计划已批准、Draft PR 已回读、结果已确认。
3. 先区分产品缺陷与前置条件缺失，再修复重复出现的卡点。
4. 每个计数闭环都要独立回读公开 Issue 与 Draft PR。
5. 只在 Issue #49 发布聚合进度，不公开身份或私有证据。
6. 达到外部 10/10 后更新增长记分卡，再决定是否进入默认分支或发布不可变 Release。
7. 最后由维护者用自己的语言准备大范围社区发布。

这是一份可审阅的发布素材。Foursday 不会自动发帖、发送邀请、上传社交预览或修改 Release。
