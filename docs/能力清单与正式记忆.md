# 能力清单与正式记忆

## 1. 为什么需要这两层

AI 能调用工具，不代表它有权执行。每个项目必须先声明能力范围；每条长期记忆必须先确认来源和有效期。

```mermaid
flowchart TD
    A["钉钉或 Codex 工作请求"] --> B{"唯一匹配请求人有权使用的项目"}
    B -->|"不能"| B1["不建立计划，提示补充项目"]
    B -->|"可以"| C["生成目标、步骤、参数和验收标准"]
    C --> D["读取该项目能力清单"]
    D --> E{"逐能力检查范围、有效期和次数预算"}
    E -->|"未登记、越界或预算不足"| E1["拒绝并记录稳定原因"]
    E -->|"允许"| F["登记可执行计划"]
    E -->|"需要审批"| G["生成绑定完整计划与授权快照的哈希"]
    G --> H{"负责人审批"}
    H -->|"拒绝、过期或计划被修改"| E1
    H -->|"批准"| F
    F --> I["执行前再次核对来源任务与人工接管"]
    I --> J["原子扣减次数预算并领取执行租约"]
    J --> K["逐步骤执行、回读和保存证据"]
    K --> L{"结果状态"}
    L -->|"成功"| M["生成原会话结果草稿"]
    L -->|"失败"| N["保留失败证据并等待处理"]
    L -->|"外部副作用未知"| O["禁止自动重试，转人工核销"]
```

正式记忆与工作计划是两条独立链路。执行授权不能让普通消息或工作计划候选绕过人工确认。唯一自动确认通道是项目另行固定来源文件、事实前缀和保留期，并明确启用低风险自动确认；来源变化、冲突、敏感内容或范围不符都会停止自动转正。

```mermaid
flowchart TD
    A["本批新消息或人工提交的已授权知识事实"] --> B{"是否是明确、稳定、未来可复用的事实"}
    B -->|"否"| B1["不生成候选"]
    B -->|"是"| C{"项目事实能否唯一匹配已授权项目"}
    C -->|"不能"| B1
    C -->|"可以或非项目事实"| D["绑定真实来源编号、版本和有效期"]
    D --> E{"凭据、PII、敏感评价或越权内容检查"}
    E -->|"命中"| E1["拒绝入库并留下脱敏审计"]
    E -->|"通过"| F{"同一事实字段是否已有记忆"}
    F -->|"完全重复"| F1["复用既有候选，不重复创建"]
    F -->|"内容冲突"| G["标记冲突并展示旧、新事实"]
    F -->|"没有"| H["建立 proposed 候选"]
    G --> I{"负责人明确选择替代旧记忆"}
    H --> J0{"固定来源、低风险、无冲突且已显式授权自动确认？"}
    J0 -->|"否"| J{"负责人确认"}
    J0 -->|"是"| M["成为正式记忆"]
    I -->|"否"| K["保持候选，不改变正式记忆"]
    I -->|"是"| L["撤销旧记忆并确认新记忆"]
    J -->|"拒绝"| K
    J -->|"确认"| M
    L --> M
    M --> N{"检索时仍满足项目、来源、权限和期限吗"}
    N -->|"是"| O["仅注入当前任务需要的内容"]
    N -->|"否"| P["暂停使用、过期或撤销"]
    O --> Q["记录本次使用来源"]
    M --> R["支持撤销、分级导出和绑定确认的永久擦除"]
```

## 2. 项目能力清单

每个项目使用一份 JSON 清单，示例见[项目能力清单示例](../deploy/项目能力清单.example.json)。

可用 `npm run projects:create -- --project-id <编号> --name <名称> --root <Git根目录> --requester <钉钉用户ID>` 先预览安全默认清单；只有显式增加 `--write` 才写入运行目录。生成器不会自动开放 gbrain、待办、日程、日志、共享文档、测试、推送或发布。

| 字段 | 作用 |
|---|---|
| `projectId` | 稳定项目编号，不使用个人姓名 |
| `rootDirectory` | 允许处理的唯一项目根目录 |
| `requesters` | 可以下达该项目任务的钉钉账号 |
| `capabilities` | 能力及自动、需审批或禁用状态 |
| `expiresAt` | 单项能力授权的失效时间 |
| `maxRuns` | 同一项目授权版本下，该能力跨全部计划最多启动的次数；执行开始即扣减，失败或取消不返还，修改授权会形成新的独立预算 |
| `timeoutMs` | 运行时间上限 |

开启办公写入时必须固定人员范围，不能让消息临时指定任意账号：

```json
{
  "dingtalk_todo_create": {
    "mode": "approval_required",
    "allowedExecutorUserIds": ["已核实的钉钉用户ID"],
    "allowedPriorities": ["20", "30"],
    "maxTitleChars": 120,
    "maxRuns": 1
  },
  "dingtalk_calendar_create": {
    "mode": "approval_required",
    "allowedAttendeeUserIds": ["已核实的钉钉用户ID"],
    "allowedRoomNames": ["永澄亭"],
    "maxDurationMinutes": 120,
    "maxTitleChars": 120,
    "allowRecurrence": true,
    "allowedRecurrenceTypes": ["daily", "weekly"],
    "maxRecurrenceCount": 10,
    "maxRuns": 1
  },
  "dingtalk_report_submit": {
    "mode": "approval_required",
    "templateId": "从 DWS 模板列表核实的模板编号",
    "templateName": "项目日报",
    "fields": [
      { "name": "今日完成", "sort": "0", "type": "1" },
      { "name": "明日计划", "sort": "1", "type": "1" }
    ],
    "maxContentBytes": 102400,
    "maxRuns": 1
  }
}
```

写入必须同时通过两道相互独立的门禁：生产配置的
`AI_EMPLOYEE_ALLOWED_CAPABILITIES` 必须显式包含
`project_memory_proposal`，且具体项目清单必须包含上述受限授权。默认全局配置不开放该能力。

开启 gbrain 读取时也必须固定项目知识路径，不能开放整个个人知识库：

```json
{
  "knowledge_read": {
    "mode": "automatic",
    "allowedSlugPrefixes": ["projects/example/"],
    "maxPages": 5,
    "maxContentBytes": 65536,
    "timeoutMs": 30000
  }
}
```

计划中的 `knowledge_read.inputs.slugs` 只能填写白名单内的精确 slug。当前不提供无范围语义搜索、模糊匹配、已删除页面读取或 gbrain 写入；研究、文档和代码步骤还必须通过 `knowledgeStepIds` 显式引用更早的知识读取步骤。

工作图不会把“排在前面”解释成“自动获得上一步内容”。研究、文档和代码步骤如需使用更早的仓库活动、同项目受治理工作历史、研究或文档证据，必须通过 `inputs.evidenceStepIds` 显式引用更早的只读步骤。执行器只接收已完成且类型匹配的证据，并限制引用数量与总正文大小；缺失、后序、重复、类型伪造或过大的证据一律拒绝。项目配方影子验证还会把历史导入中已经核验的来源路径作为精确研究范围交给只读运行时，避免扫描未授权文件。

未登记能力、越界目录、未授权请求人和过期授权一律拒绝。L4 能力即使配置为自动，也仍然强制单次审批。代码合并当前是人工专属动作：AI 可以准备补丁、分支、测试和合并建议，但能力目录不提供自动合并入口。

白名单联系人直接问“你能做什么”或“有哪些能力”时，系统使用确定性能力自述，不调用 Codex 生成答案。它只汇总当前全局开关和请求人匹配项目中未禁用、未过期的能力，并同时说明发送与计划执行是否开启。私聊可显示请求人获准的项目名称；群聊只显示项目数量，避免把项目关系暴露给同群其他成员。自述不会输出项目目录、命令编号、钉钉账号、其他请求人的项目或密钥；项目清单读取失败时明确要求到管理台核对，不会猜测。这里展示的是配置与授权状态，真正执行仍须重新通过运行时、策略、审批和回读验收。

私聊近期上下文与正式记忆是两层不同能力。近期上下文只在同一联系人、同一会话内读取源消息之前 24 小时的有界历史，用当前源消息识别对方开放身份，再把历史标为“当前账号 / 对方 / 未知”；读取失败时不生成草稿。两分钟内的续发会使未发送旧草稿和旧审批失效。这些历史不会因此自动成为正式记忆。职责、公开偏好、协作关系或项目事实仍必须形成来源绑定候选，经过既有敏感信息过滤、冲突检查和本人确认后才可长期复用。

项目身份注册表是正式项目记忆的最小入口，只保存项目编号、规范名称和本人确认的别名，不保存目录或正文，也不开放能力。运行 `npm run projects:identities` 只返回当前注册表摘要和 `PROJECTS-...` 确认值；只有增加 `--apply --confirmation 当前值` 才新增并确认完全一致的项目身份记忆。已有相同身份保持幂等，别名变化或歧义会停止，不能静默覆盖。对话只加载显式或 24 小时会话内最近明确命中的项目，不把全部项目记忆注入每次聊天。

```bash
mkdir -p .runtime/projects
cp deploy/项目能力清单.example.json .runtime/projects/示例项目.json
npm run projects:validate
```

## 3. 完整任务计划

任务计划示例见[任务计划示例](../deploy/任务计划.example.json)。每个步骤必须说明能力、目标和验收证据；有副作用的步骤还必须说明回滚方式。

固定模板日志可参考[钉钉日志任务示例](../deploy/钉钉日志任务.example.json)。示例字段名必须替换为项目清单中已从 DWS 模板详情核实的完整字段集合，不能只填写其中一部分。

钉钉消息只有被识别为明确工作请求时才会进入计划提案；普通问答和闲聊仍只生成回复草稿。提案器只查看请求人已被项目清单授权的项目：唯一项目可直接起草，多个项目必须由消息明确给出项目名或编号，否则停止并要求澄清。提案不会自动执行。

```bash
npm run plan:check -- .runtime/projects/示例项目.json \
  < deploy/任务计划.example.json
```

输出只有四种结论：`ALLOW`、`REQUIRE_APPROVAL`、`ASK_FOR_INFORMATION`、`DENY`。审批必须绑定 `planHash`；项目、步骤、参数或风险改变后，原审批自然失效。

把评估后的计划登记到 PostgreSQL，并进行单次审批：

```bash
npm run control -- plan-register .runtime/projects/示例项目.json \
  < deploy/任务计划.example.json
npm run control -- plan-show <计划ID>
npm run control -- plan-approve <计划ID> '同意本计划，不授权计划外动作'
```

批准票据默认 2 小时有效、最多消费一次。计划哈希不一致、票据过期或已经消费时，执行入口必须拒绝。

当前接入的项目执行适配器：

| 能力 | 真实动作 | 验证方式 |
|---|---|---|
| 知识页读取 | gbrain 按项目白名单内的精确 slug 只读获取 | 返回 slug 与请求完全一致、页面未删除、正文限长并记录哈希 |
| 研究 | Codex 在项目目录中只读分析 | 非空、限长、内容哈希 |
| 文档草稿 | 生成中文 Markdown 草稿 | 非空、限长、内容哈希 |
| 共享文档创建 | DWS 创建到项目固定文件夹或知识库 | `doc read` 回读内容哈希一致 |
| 待办创建 | DWS 为清单内固定执行人创建待办 | 取返回任务 ID，再执行 `todo task get` 回读 |
| 日程创建 | DWS 创建限时、限参与人的普通或有界循环日程；会议室先按白名单名称实时搜索 | 搜房必须唯一命中合法 `roomId`；创建后执行 `calendar event get` 回读 |
| 日志提交 | DWS 按清单固定模板提交完整字段 | 提交前核对模板编号、名称和字段结构，提交后执行 `report entry get` 回读 |
| 代码补丁 | 生成 unified diff，不写工作区 | `git apply --check` |
| 隔离分支 | 在独立 worktree 应用补丁并创建本地提交 | 提交差异哈希与补丁证据一致 |
| 本地测试 | 只运行清单登记的绝对可执行文件和固定参数 | 退出码、耗时、输出字节数和哈希 |
| Git 推送 | 推送受控前缀分支 | `ls-remote` 回读相同提交 |
| 生产发布 | 运行登记的发布命令和验收命令 | 验收退出码为 0；失败执行登记回滚并复验 |

```bash
npm run control -- plan-register .runtime/projects/示例项目.json \
  < deploy/只读执行任务.example.json
npm run control -- plan-approve <计划ID> '批准当前哈希对应的只读计划'
npm run control -- plan-execute <计划ID> .runtime/projects/示例项目.json
npm run control -- plan-evidence <计划ID>
```

执行前会重新读取项目清单。计划哈希同时绑定任务内容和完整项目授权快照；目录、命令、参数、远端、超时或授权变化后，旧审批不能继续使用。所有步骤先完成适配器预检，再消费审批票据。没有适配器、命令未登记、远端不一致或工作目录越界时，不会消耗票据。

本地测试使用最小环境变量集合，不继承数据库、钉钉或告警密钥。命令输出正文不进入日志或证据，只保存退出码、字节数和 SHA-256。需要诊断失败时，应在隔离 worktree 中由负责人复跑，而不是扩大后台日志范围。

隔离 worktree 在成功后保留，便于人工审查和后续推送；失败计划也保留现场。清理由负责人根据证据中的 worktree 和分支执行，远端分支删除必须使用新的审批计划。

## 4. 正式记忆

| 状态 | 能否用于工作 | 说明 |
|---|---|---|
| 候选 | 否 | 只记录建议，不作为事实 |
| 已确认 | 是 | 仍受项目、范围和有效期约束 |
| 已撤销 | 否 | 立即停止引用 |
| 已过期 | 否 | 保留审计记录，不参与检索 |

新增候选时，正文从标准输入读取，避免出现在命令参数和进程列表中：

```bash
echo '交付前必须核对实际批次覆盖。' | \
  npm run control -- memory-propose project 单词项目 document 文档编号 vocab_project

npm run control -- memory-confirm <记忆ID>
echo '批次覆盖' | npm run control -- memory-search project 单词项目
npm run control -- memory-revoke <记忆ID>
```

纠正、导出和永久删除使用独立的显式入口：

```bash
# 新记忆确认时显式替代旧事实
npm run control -- memory-confirm <新记忆ID> <旧记忆ID>

# 默认只导出不含主题、正文、来源编号和范围的元数据
npm run control -- memory-export /绝对路径/记忆元数据.json all metadata

# 完整正文导出必须输入固定确认词，目标文件必须不存在
npm run control -- memory-export /绝对路径/项目记忆.json <项目编号> content EXPORT-CONTENT

# 先预览绑定当前记忆编号的删除确认值，再单独执行
npm run control -- memory-delete-preview <记忆ID>
npm run control -- memory-delete <记忆ID> <上一步确认值>

# 立即复核来源；后台服务每 5 分钟自动复核全部有效 gbrain 记忆
npm run control -- memory-source-check <记忆ID>
npm run memory:sources
```

导出文件以 `600` 权限创建且绝不覆盖已有文件；完整导出会包含明文业务内容，应由负责人自行保管和删除。永久删除会擦除记忆的主体、陈述、来源、范围、项目和创建人字段，只保留无法参与查询的无正文墓碑与最小审计事件，不提供恢复。管理台不提供一键永久删除，避免误操作。

长期记忆采用“Markdown/gbrain 权威正文 + PostgreSQL 运行投影”：Git 管理的 Markdown 供人阅读、修改和审计；gbrain 负责写入、精确读取、实体与图谱；Foursday PostgreSQL 只保存加密短句投影、原始来源、项目范围、状态、版本、访问租约和审计。gbrain 自己使用的 PostgreSQL 是可从 Markdown 重建的知识索引，不与 Foursday 的事务库混为一谈。

记忆内容分为四类并列范围：工作记忆、情景记忆、语义记忆和前瞻记忆。人物、项目、原则与知识属于语义记忆的并列命名空间；项目不是被夹在人物和原则之间的“层级”。整理、去重、过期与检索是统一生命周期服务。

Foursday 管理的低风险语义候选使用确定性的 `atoms/foursday/` 页面。写入前拒绝凭据、机密、PII 和敏感人物材料；页面只保留来源与主体的不可逆摘要。gbrain 写入后必须逐字回读 statement，并核对精确 slug、内容摘要和版本，随后才建立可检索的 PostgreSQL 投影。冲突或自动确认失败时保留 `proposed` 隔离态，不参与回复。

外部项目知识页仍必须使用 `project` 或 `knowledge` 类型并绑定项目。确认前系统实时校验项目仍开放 `knowledge_read`、授权未过期、精确 slug 仍在项目前缀内、页面可读且版本一致；通过后只签发不超过项目授权期限的短期访问租约。Foursday 自己的 `atoms/foursday/` 权威页不依赖单个项目的知识读取能力，但同样必须持有短期回读租约和内容摘要。`com.foursday.memory-source` 每 5 分钟复核；租约过期、页面变化或读取失败会立即停止使用，不能拿 PostgreSQL 旧投影继续回答。

生产默认设置 `AI_EMPLOYEE_MEMORY_AUTHORITY_MODE=gbrain`，因此预检始终验证 gbrain。`AI_EMPLOYEE_MEMORY_AUTHORITY_WRITE` 和 `AI_EMPLOYEE_MEMORY_AUTHORITY_AUTO_CONFIRM` 是两个独立开关，默认均为 `false`；自动确认只有在写入已显式开放时才能启用。它们不打开消息发送、计划执行或主动工作。

### 4.1 导入历史项目

历史项目导入不是把聊天记录和文档整包塞进提示词。导入包必须声明项目身份、项目内来源文件和准备形成的记忆候选；每条候选都要附一段确实存在于源文件中的短引文。系统只保存必要陈述、项目范围、相对源路径、文件摘要和引文摘要，不复制整份历史文件。

参考 [`examples/historical-project-import.json`](../examples/historical-project-import.json) 准备导入包后，先运行只读预览：

```bash
AI_EMPLOYEE_CONFIG_FILE=.runtime/production.json \
  npm run projects:import -- --bundle /绝对路径/历史项目导入.json
```

预览会核对 Git 根目录、项目身份、记忆范围、普通文本文件、路径边界、文件摘要、引文、凭据和人员敏感信息，并对当前数据库中的候选和正式记忆做重复、冲突检查。输出的 `confirmation` 绑定这次项目清单、文件内容和数据库状态。只有再次提交当前确认值才会写入：

```bash
AI_EMPLOYEE_CONFIG_FILE=.runtime/production.json \
  npm run projects:import -- --bundle /绝对路径/历史项目导入.json \
  --apply --confirmation IMPORT-XXXXXXXXXXXX
```

显式应用最多创建项目清单和 `proposed` 候选，不会确认记忆、运行配方、发送消息或修改任何外部系统。重复导入保持幂等；与正式事实冲突的候选必须在管理台明确选择替代旧事实。源文件变化、数据库状态变化或导入包变化都会使旧确认值失效。长文档更适合继续保留在 gbrain，通过项目白名单内的精确 slug 只读使用。

个人工作台提供同一契约的图形入口：浏览器只解析用户选择的本机 JSON 包，本机回环服务再读取包中声明的项目内相对来源。浏览器所有者会话或只读令牌可以查看来源、候选、安全跳过、重复、冲突和当前摘要，不创建项目目录或记忆；显式应用还必须具有会话写权限或写入令牌，并由本人手工输入预览中的 `IMPORT-...` 确认值。服务端会重新核对来源和数据库状态，错误或过期摘要保持零写，成功后正式记忆数量仍为 0。登录只替代反复粘贴令牌，不替代内容绑定确认。

### 4.2 项目配方影子验证

历史项目导入后，可以先在完全隔离于生产数据库的本地证据账本中演练项目已经选择的配方。默认命令只校验导入来源、干净 Git 提交、项目范围、配方输入、能力策略和计划哈希；不会调用模型或创建文件：

```json
{
  "projectFocus": "核对首个真实里程碑并形成跟进草稿"
}
```

```bash
npm run projects:shadow -- \
  --bundle /绝对路径/历史项目导入.json \
  --recipe project-follow-up \
  --values /绝对路径/配方输入.json
```

只有显式增加 `--run` 才调用选择的 Codex 或 Claude Code 只读运行时，并且输出目录必须是尚不存在、父目录不经过符号链接的绝对路径：

```bash
npm run projects:shadow -- \
  --bundle /绝对路径/历史项目导入.json \
  --recipe project-follow-up \
  --values /绝对路径/配方输入.json \
  --output /绝对路径/新的影子证据目录 \
  --runtime codex --run
```

影子入口只接受确定性的 `repository_activity_read`、`project_work_history_read`、`research` 和 `document_draft`。日报图把同一日期窗口内的精确 Git 活动，以及同项目终态计划和步骤回读摘要通过两条显式证据边传给研究步骤；影子运行的工作历史只来自隔离账本，不会执行 Git 写入或读取生产库。代码、记忆写入、消息、待办、日程、共享文档、Git 写入和发布步骤全部失败关闭。运行前后必须保持同一干净 Git 提交和同一来源摘要。输出目录只包含权限为 `600` 的隔离 SQLite 账本、完整证据 JSON、失败证据或中文审阅说明；不读取生产配置，不连接生产数据库，不触碰外部业务系统，不写入或确认记忆和生产时间返还。模型运行时本身可能访问其模型服务，因此不能把“外部业务系统零写”误解为完全离线。基线耗时只用于向本人提问；在本人填写 AI 交付后的真实审阅、核对、补充和修改时间之前，状态始终是 `awaiting_user_review_time`。

运行成功会返回证据 SHA-256 和由其派生的 `REVIEW-...` 口令。本人阅读交付物后，可以把真实投入分钟写入隔离账本：

```bash
npm run projects:shadow -- \
  --review /绝对路径/新的影子证据目录 \
  --evidence-sha256 64位摘要 \
  --human-minutes 10 \
  --confirm REVIEW-前12位
```

确认前会逐项核对不可变证据 JSON、隔离账本中的完整计划和步骤回读证据，并复用生产时间返还的同一计算规则。成功后只新增权限为 `600` 的 `本人确认.json` 并在隔离账本标为已确认；重复执行保持幂等，仍不连接或更新生产时间返还账本。

RC 后候选增加了独立的纳入入口。默认命令只预览，不连接或写入生产数据库：

```bash
npm run projects:shadow:admit -- \
  --evidence-directory /绝对路径/新的影子证据目录 \
  --evidence-sha256 64位摘要
```

预览会重新核对证据 JSON、隔离 SQLite 计划与步骤、`本人确认.json`、项目是否已接入、配方是否仍被项目选择，以及配方基线是否发生变化。只有第 022 号迁移已部署、预览给出的 `ADMIT-...` 口令再次显式传入时，才允许写入：

```bash
npm run projects:shadow:admit -- \
  --evidence-directory /绝对路径/新的影子证据目录 \
  --evidence-sha256 64位摘要 \
  --apply --confirmation ADMIT-前12位
```

这条路径只导入一条已由本人确认的时间返还证明，按证据 SHA 幂等；它不会复制影子工作计划到生产、不会形成项目记忆，也不会触发消息、办公、Git 或发布动作。驾驶舱把它与生产计划确认证据统一汇总，但会分别显示来源数量。当前代码仍是 RC 后本地候选，尚未提交、部署或写入生产。

### 4.3 项目记忆自动同步

人工导入只负责首次接入，不应成为日常维护方式。项目可以在能力清单中一次性授权 `project_memory_proposal`，固定允许读取的相对文件、事实字段前缀、最长保留期和低风险自动确认策略：

```json
{
  "mode": "automatic",
  "expiresAt": "2026-11-11T00:00:00.000Z",
  "allowedFactKeyPrefixes": ["decision.", "principle.", "milestone."],
  "maxRetentionDays": 90,
  "sourcePaths": ["README.md", "docs/decisions.md"],
  "autoConfirm": true
}
```

之后可用 Codex 或 Claude Code 自动扫描这些固定文件。运行时只把固定文件的副本放入临时工作目录，不把整个项目作为模型工作区：

```bash
# 默认只预览：会调用模型，但不写数据库。
AI_EMPLOYEE_CONFIG_FILE=.runtime/production.json \
  npm run projects:memory:sync -- --project 项目编号 --runtime codex

# 项目清单已选择 automatic 后，可按一次授权持续应用。
AI_EMPLOYEE_CONFIG_FILE=.runtime/production.json \
  npm run projects:memory:sync -- --project 项目编号 --runtime codex --apply
```

系统仍会逐条执行精确引文、文件摘要、路径、凭据、个人敏感信息、事实前缀、保留期、重复和冲突检查。只有置信度为 1、非机密、来源未变化且不存在冲突的事实才允许自动确认；冲突、越界、敏感或来源漂移都停止自动处理或进入人工例外队列。若能力模式是 `approval_required`，每次应用仍需输入当前 `SYNC-...` 摘要；若为 `automatic` 且 `autoConfirm: false`，可以自动创建候选，但仍不自动转正。调度该命令不会自动开启消息发送、计划执行或主动工作。

个人工作台先提供项目记忆授权向导，因此普通用户不必手改 JSON。双令牌零写设置预览会核对当前项目清单、非符号链接的普通来源文件及其摘要、事实前缀、不得超过项目范围的保留期、最长 365 天的授权期限和自动确认边界，并派生精确 `MEMORY-AUTH-...` 确认值。应用继续要求双令牌，重新计算同一预览后只原子替换权限为 `0600` 的项目清单；它不会把 `project_memory_proposal` 加入全局能力，因此仅设置项目不会启动后台同步。

个人工作台另提供显式的单次同步入口。由于生成预览会调用已配置模型服务，开始生成就必须提供写入令牌；预览本身不写数据库。模型生成包不会返回浏览器，而是在本机服务内存中保存十分钟，页面只看到有界候选摘要和不透明编号。每份预览只能应用一次；应用时重新加载当前项目，复核全局能力、项目授权期限、固定来源、事实前缀、记忆状态和确认摘要。`automatic + autoConfirm` 也只能沿用项目此前明确授权的低风险规则，页面不能临时扩大范围。

生成的待审候选直接回到所属项目卡片。驾驶舱每个项目最多返回 20 条本项目候选，不能混入其他项目；普通确认和拒绝都要求写入令牌。若候选与现有正式事实冲突，页面必须展示旧事实，并把“明确替代”绑定到该旧记忆编号；已有重复事实只允许拒绝，不能再次确认。确认后才进入正式记忆和后续工作上下文。

持续自动维护可运行独立同步循环：

```bash
AI_EMPLOYEE_CONFIG_FILE=.runtime/production.json \
  npm run projects:memory:watch -- --interval-minutes 60
```

全局能力关闭时，循环不会读取项目清单、调用模型或写检查点；全局开放后也只处理记忆能力为 `automatic` 且授权未过期的项目。过期项目会在读取来源和调用模型前停止，手动同步入口执行同一到期门禁。每轮先计算授权来源摘要，未变化时不调用模型，成功写入后才推进检查点，失败会在下一轮重试。它与消息发送、项目计划执行和主动工作开关相互独立。

需要维护唯一值的记忆必须在 `scope.factKey` 标出事实字段，例如“发布口径”或“首选称呼”。同项目、同类型、同主题、同事实字段只允许一个有效值：新候选完全相同则判为重复，陈述不一致则必须明确选择“替代旧记忆”，系统在同一事务中确认新事实并撤销旧事实。没有事实字段的多条相关备注可以并存，避免把“沟通偏好”和“机密备注”等不同事实误判为冲突。若历史上已经出现多个相互矛盾的已确认事实，系统停止自动处理，必须先由负责人逐条撤销。

回复草稿只会自动读取“已确认、未过期、未撤销、非机密”的原则记忆，以及与当前联系人唯一账号匹配的人物记忆。项目记忆只有任务明确绑定项目后才能读取，避免跨项目串用。

## 5. 当前执行边界

当前运行时已经能验证项目能力、评估完整计划、管理正式记忆，并执行项目级精确知识页读取、研究、文档草稿、共享文档创建、受控待办、受控日程、固定模板日志、代码补丁、隔离提交、本地测试、受控推送和生产发布。知识页读取只接受项目白名单前缀内的精确 slug，且只有被后续步骤显式引用时才进入 Codex 上下文。待办只允许清单中的执行人和优先级；日程只允许清单中的参与人、时长和会议室名称，会议室 ID 必须在执行时按同一时段搜索且唯一命中，循环只开放有次数上限的按日/按周规则；日志同时绑定模板编号、名称和完整字段结构，模板漂移会停止提交。OA 审批可以作为只读信息进入方案，但同意、拒绝和转交不提供执行适配器。高风险能力默认没有任何真实项目授权；只有负责人创建项目清单并批准具体计划哈希后才能运行。生产数据修改不提供通用适配器，必须按具体系统单独建模。

## 6. V2.3 配方、主动工作与项目记忆

工作配方不是能力授权。它只是把一组重复步骤、输入 Schema、配方版本和用户确认的基线耗时保存为模板；实例化后每一步仍必须通过当前项目清单、预算、风险和审批。个人工作台使用统一工作委托单，一次展示配方的全部类型化输入，不再用连续弹窗拆散上下文；随后必须先用只读令牌预览完整步骤、风险、验收证据和精确计划哈希，只有写入令牌再次提交同一哈希时才登记计划。配方、输入、请求人或授权发生变化都会导致哈希不一致并要求重新审阅；工作台登记一律进入待审批，即使全局计划执行已开启也不能自动执行。定时工作还会在同一张委托单中展示首次运行时间、间隔、每日次数与冷却期；保存时必须提交刚审阅的计划哈希，并且创建结果仍是停用状态。

| 配方 | 默认流程 | 记忆与副作用边界 |
|---|---|---|
| 日报 | 汇总事实→文档草稿→结果回报 | 不自动提交日志，除非项目单独授权对应能力 |
| 项目跟进 | 核对进度→形成跟进文档→结果回报 | 不把推测写入正式记忆 |
| 项目记忆更新 | 核对证据→形成审查文档→项目记忆候选 | 候选必须绑定已完成文档证据摘要；不自动替代冲突事实 |
| 会议跟进 | 会议记录→文档→项目记忆候选→待办→跟进日程 | 决策只写候选；待办和日程逐项审批并回读 |
| 代码交付 | 补丁→隔离分支→固定测试→推送→Draft PR | 不合并 PR、不变更生产、不运行未登记命令 |

```mermaid

    A["消息、会议或触发器产生计划"] --> B{"唯一匹配请求人有权使用的项目"}
    B -->|"否"| C["停止并请求本人选择项目"]
    B -->|"是"| D["实例化带版本配方"]
    D --> E["凭据、PII、敏感评价或越权内容检查"]
    E -->|"不通过"| C
    E -->|"通过"| F["能力、范围、预算与风险评估"]
    F -->|"待审批"| G["本人核对完整计划哈希"]
    F -->|"允许"| H["执行并回读"]
    G -->|"批准"| H
    G -->|"拒绝 / 人工接管"| C
    H --> I["项目记忆候选"]
    I --> J{"来源计划仍可核对且本人确认吗"}
    J -->|"冲突"| K["负责人明确选择替代旧记忆"]

```

项目驾驶舱只汇总已授权项目的目标、里程碑、计划、步骤证据、交付物、正式记忆、触发器和已确认返还时间。主动触发器默认停用；启用、执行和隐私擦除分别重新校验。按人员擦除还会纳入该人员工作计划派生的项目记忆，避免只删除消息记忆而遗留计划记忆。
