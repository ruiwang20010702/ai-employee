# AI 员工

完整设计见 [设计总览](./docs/设计总览.md)。

当前仓库中的代码只是钉钉消息监听与分流原型，不是生产版 AI 员工。

这个原型使用钉钉本地同步点与消息索引文件的变更作为唤醒信号，再通过 DWS 获取正式消息。
它不会打开或解析钉钉的私有数据库，也不会自动发送任何回复。复杂消息只会进入
Codex 任务队列；当前尚未实现生产级队列工作器。

当前一次监听一个通过环境变量配置的联系人。仓库不保存真实联系人、聊天内容或凭证。

## 运行

```bash
npm run check
DINGTALK_TARGET_USER_ID="<钉钉 userId>" npm run listen
```

首次运行只建立消息基线，不会把历史消息误判成新消息。收到新消息后：

1. 事件输出到终端并追加到 `.runtime/events.jsonl`。
2. 本地策略判断是否需要回复，并记录具体原因。
3. 问题、任务、方案或代码请求会进入 `.runtime/codex-task-queue.jsonl`，不会阻塞消息监听。
4. 普通草稿保存到 `.runtime/drafts/`，同时追加到 `.runtime/pending-drafts.jsonl`。

草稿只供审核，不会自动发送。

默认不回复的情况包括：

- 确认、致谢和对话闭环，如“收到”“好的”“辛苦了”。
- 对方明确表示“不用回”“你先忙”“晚点再说”。
- 只有表情、图片或附件占位。
- 自动通知。
- 很短的连续输入片段。
- 没有问题或行动要求的普通告知。

包含问题、请求、故障、紧急风险、方案、代码、测试、上线和排期等内容时，
才进入 Codex 任务队列。

可选环境变量：

- `DINGTALK_TARGET_USER_ID`：监听的联系人 userId。
- `DINGTALK_DEBOUNCE_MS`：本地事件防抖时间，默认 800 毫秒。
- `DINGTALK_FALLBACK_MS`：漏消息兜底检查间隔，默认 5 分钟。
- `DWS_PATH`：DWS 可执行文件路径。
- `DINGTALK_CODEX_INLINE=true`：实验选项，在监听进程内直接启动 Codex；默认关闭，避免冷启动阻塞。

按 `Ctrl+C` 停止监听。

## 配置与隐私

1. 复制 `.env.example` 了解所需变量，但不要提交真实 `.env`。
2. 使用 `dws contact user search --query "<姓名>" --format json` 获取联系人 userId。
3. 运行时注入 `DINGTALK_TARGET_USER_ID`，不要把真实 ID 写入代码。
4. `.runtime/` 保存本地消息事件、状态和草稿，已被 Git 忽略。
5. 不要把 DWS 凭证、聊天记录、联系人标识或项目秘密提交到仓库。

## 当前边界

- 这是研究与验证原型，不是可直接投入生产的自动回复服务。
- 当前不会自动发送钉钉消息。
- 本地钉钉文件变化只用于唤醒；正式消息内容通过 DWS 获取。
- 复杂任务只进入本地队列，生产级 Codex Worker 尚未实现。

## 安全问题

发现安全或隐私问题时，请不要在公开 Issue 中粘贴消息正文、联系人 ID、令牌或日志。处理方式见 [安全说明](./安全说明.md)。
